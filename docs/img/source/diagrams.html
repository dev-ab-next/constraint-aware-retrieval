Repository walkthrough

What this project is about, the data, and how it works

AI assistants that help fix GPU problems look up a troubleshooting procedure, then follow it. Search finds procedures that sound right. This project shows that they often don't fit the actual GPU, and tests a simple fix: check each procedure's conditions against the GPU's real numbers before the assistant sees it.

1 · The idea in one picture

Two procedures can sound the same and mean opposite things

An operator asks: "We're seeing ECC errors on gpu-0039. How should we handle it?" Two procedures in the runbook both talk about GPU memory errors:

"Corrected errors, low rate: monitor"

Applies when: 1–99 corrected errors today and no uncorrected errors this week

Action: leave it running.

"Uncorrected error (class B): drain and reboot"

Applies when: 1 or more uncorrected errors today, on a class B GPU

Action: take it out of service.

A search engine sees almost the same words. The difference is a number in the GPU's health data. gpu-0039 had 4 uncorrected errors today, so only the second procedure is right. Picking the first would leave a failing GPU running jobs.

2 · The data

Four pieces of data, all synthetic

Everything is invented for the test, so the right answer to every question is known. There are four pieces, and each lives in its own folder of the repository.

② Questions

200 questions, one per GPU, written the way an operator would ask. The question describes the symptom. The deciding numbers are only in the GPU's data. There are five kinds, 40 each:

③ Procedures

26 runbook procedures for six kinds of problems: GPU memory, temperature, PCIe, GPU-to-GPU links, power, and server memory. Each is a short text file. The key part is at the top: the conditions under which it applies, written as data.

id: PROC-005
title: "Uncorrected GPU memory error (class B): drain and reboot to retire pages"
device_classes: [class_b]                 # only for class B GPUs
preconditions:
  - {metric: ecc_uncorrected, window: 24h, op: ">=", value: 1}   # 1+ uncorrected errors today
---
Steps:
1. Cordon the node and drain all workloads...

Folder: data/corpus/procedures/. Five procedures are generic "collect the logs first" steps with no conditions, one for each topic except server memory.

3 · The implementation

Five ways to pick procedures, each adding one step

Each setup takes the question and returns its top 3 procedures. C1 to C4 are standard retrieval setups. C5 is the idea being tested. For C1 to C4, the GPU's numbers are pasted into the question as text, which is the common shortcut.

The check in C5

For each procedure in C4's list, C5 compares its conditions with the GPU's real numbers and gives one of three verdicts:

Two rules: missing data never counts as a pass, and the check only removes procedures. It never changes their order.

First suggestion was the specific right one: C1 21%, C2 21%, C3 22%, C4 27%, C5 54%. The check itself takes about 2 ms per question.

  • Without the check, the first suggestion didn't fit the GPU in about two out of three questions.
  • The usual upgrades didn't fix it. Keywords made it worse, because the pasted numbers match runbook text by accident.
  • The check doubled the hit rate by clearing out procedures that can't apply.
Read the 0% carefully. C5 checks the same conditions used to build the answer key, so in this test it can't break them. The finding is that the other setups break those conditions most of the time.
5 · Stress tests

What happens when the inputs are imperfect

Missing data stays safe

Up to half of each GPU's measurements deleted. C5 found fewer right procedures (90% → 64%) but never passed a bad one off as checked. It flagged them as "couldn't check" instead.

Wrongly written conditions gets fooled

Some conditions deliberately broken. With 1 in 10 wrong, a procedure that didn't fit got through unflagged in 26% of questions. With 1 in 4 wrong, 54%. The conditions need careful review.

One more limit: the check removes wrong answers but can't find missing ones. Generic "collect logs" procedures always pass, so they sometimes crowd out the specific right one.
